# お題の自動生成 — 設計 v0.1

作成 2026-08-29 / [SPEC.md](./SPEC.md) §9 の中身

---

## 0. 前提にした調査

別途行った実測調査を土台にする。要点だけ再掲する。

- ネット大喜利4サイト 2,750題 と 生・大会側 490題 を型分類した結果、**分布がほぼ裏返っていた**。
  ネットは疑問符で締めるのが64.1%、生・大会は体言止め（設定提示型）が81.0%。
- ネット側で最多の「モノ・特徴型」は43.8%、生側では12.7%。
  逆に「問いを明示しない設定提示型」はネット5.7%、生44.5%。
- 難度を決めるのは型ではなく3つのパラメータ。**要素の数**（3つが限界）、
  **語のレベル**（誰でも連想できるほど広がる）、**語尾の絞り込み度**。
- どの型にも乗る装置として、「」の埋め込みが20.0%、仮想改変が3.9%、固有名詞が4.4%。
- ランキング・順位型は「ボケるべきか本気で答えるべきか分からず場が濁る」と名指しで指摘あり。

**この数字をそのまま真似してはいけない。** 理由を次節に書く。

## 1. このゲームに翻訳する

### 1.1 調査対象は全部「1問1答」、このゲームは「1問に何度も答える」

集めた3,240題は、ネットも生も**1つのお題に1人1回答える**前提で作られている。
このゲームは違う。回答権が無限で、全員が「次のお題に行く」を押すまで同じお題が場に残る
（[SPEC.md](./SPEC.md) §7）。**1つのお題が5回でも10回でも回答を支えなければならない。**

したがって新鮮味は2種類ある。ここを分けないと設計を誤る。

| | 何の新鮮味か | 敵 |
|---|---|---|
| **A. お題と お題のあいだ** | 毎回ちがうものが出てくる | 型・語尾・素材・骨格の反復 |
| **B. 1つのお題の中** | 同じお題で5回答えても枯れない | お題に幅がないこと |

ネット大喜利の実測分布は **A の世界の最適化しか含んでいない**。
「モノ・名称型」が43.8%を占めるのは1問1答だから成立する話で、
このゲームで半分をそれにすると、3人目あたりで答えが出尽くす。

**B を確保する条件**（採用する型を決める基準）:

- 答えの軸が複数ある。設定提示型が最強。次いで属性・特徴型。
- 正解が一点に収束しない。「名前は？」より「どんなの？」。
- 要素が2つあると、片方を固定してもう片方をずらす、という回答の広げ方ができる。

### 1.2 フリップという制約

回答は**マウスで手書きするフリップ**（[SPEC.md](./SPEC.md) §4）。長文は書けない。
一言・短文・絵で答えられる型が向き、因果を説明する必要がある型は不利になる。

- 向く: セリフ型、属性・特徴型、穴埋め型、モノ・名称型
- 不利: 理由型（「なぜなら〜」が長い）、未完・継続型

### 1.3 娯楽志向に置く

調査で立った「競技志向か娯楽志向か」の仮説で言えば、このゲームは**娯楽側**。
身内で遊ぶパーティーゲームで、全員が何か書けることを優先する。

当初は「答え方を委ねる回も2割弱混ぜる」としていた。**下見でこれが全否定された。**

体言止めで出した5問（「押し入れにだけ貼ってある張り紙」「神様が最後に残した御守り」など）は
**5問とも「語尾がほしい」と返ってきた**。生・大会で81%を占める形が、この面子では機能しない。

**結論: 体言止めは採らない。全ての型に語尾を付ける。**
生の81%という数字は「答え方を委ねられる相手だけが集まる競技の場」の数字であって、
身内で遊ぶ娯楽の場のものではなかった。§0 の「競技志向か娯楽志向か」という軸のうち、
このゲームは娯楽側に**振り切る**。

型そのものは残す。**状況提示型**（旧・設定提示型）は「前振りが厚く、語尾で軽く方向を示す」型として、
重み18のまま最多に置く。属性型との違いは前振りの厚さで付ける。

## 2. 採用する型と重み

### 2.1 重み表

| 型 | 重み | 語尾の例 | 幅(B) | フリップ適性 | ネット実測 |
|---|---:|---|:-:|:-:|---:|
| 状況提示型 | 18 | どんなの？／なんて書いてある？ | ◎ | ○ | 5.7% |
| 属性・特徴型 | 18 | どんな〜？ | ◎ | ◎ | 43.8%※ |
| 行為・展開型 | 13 | どうした？／その後どうなった？ | ○ | ○ | 6.7% |
| セリフ型 | 12 | 何と言った？／第一声は？ | ○ | ◎ | 7.4% |
| 穴埋め型 | 10 | 〇〇に入る言葉は？ | ○ | ◎ | 3.6% |
| 理由型 | 8 | なぜ？／どうして？ | ○ | △ | 9.6% |
| モノ・名称型 | 8 | 名前は？／何が出てきた？ | △ | ◎ | 43.8%※ |
| 否定評価型 | 6 | こんな〜は嫌だ | ○ | ◎ | 3.7% |
| あるある型 | 4 | ありがちなことは？ | ○ | ○ | 2.2% |
| 対比・類推型 | 2 | AはXですが、Bは？ | △ | ○ | 0.8% |
| 未完・継続型 | 1 | 〜すると… | ○ | △ | 0.3% |

※ 実測の「モノ・特徴型」43.8%は、属性型とモノ・名称型が混ざった数字。表層の語尾判定なので分離できていない。

### 2.2 実測から意図的にずらした点

| 型 | ずらし方 | 理由 |
|---|---|---|
| モノ・名称型 | 実測の最多を **8まで落とす** | 1問1答向け。正解が一点に寄り、同じお題の2人目以降が枯れる（§1.1 の B） |
| 設定提示型 | 実測ネット5.7% → **18に上げる** | B に最も強い。生・大会で81%を占めるのは、委ねられる場では機能する証拠 |
| 穴埋め型 | 実測3.6% → **10に上げる** | 生側で9.4%と高く、かつフリップと相性が良い（空欄の分だけ書けばいい） |
| 理由型 | 実測9.6% → **8** | 手書きで因果を書くのが重い |

### 2.2b 下見で落とした骨格（2026-08-29）

| 骨格 | 出た例 | なぜ落としたか |
|---|---|---|
| ha-02「{ATTR}な{PERSON}に{ACT}されたくない」 | 大胆な幼なじみに立ち読みされたくない | **日本語が安定しない。** `intrans` を弾いても「〜されたくない」が成立する行為はごく少なく、残りも不快な文になる。3要素の検証は at-05（「部長が給湯室に持ち込んだ耳栓」＝通った）が引き継ぐ |
| li-04「{ORG}の朝礼で{PERSON}が言った一言」 | 床屋の朝礼で町内会長が言った一言 | **「朝礼」が組織と人の両方に強い制約を掛ける。** 朝礼のある組織／そこに居る人、の二重条件は汎用テンプレに向かない。li-05「{ORG}の電話に出た{PERSON}の第一声」に差し替えた（電話はどの組織にもある） |

代わりに ha-03「こんな{TIME}の{PLACE}は嫌だ」と li-05 を足し、型ごとの本数は保った。

### 2.3 入れない型

| 型 | なぜ入れないか |
|---|---|
| ランキング・順位型 | 「ボケるべきか本気で答えるべきか分からず場が濁る」という現場からの名指しの指摘がある。パーティーゲームで場が濁るのは致命的 |
| 画像・写真型 | 画像素材を持たないと作れない。将来やるなら別立て（自動生成の枠には入らない） |
| 定義変換型（略語・和訳） | 調査でも「型というよりタグ運用上のジャンル名に近い」と判定保留になった。輪郭が定まってから |

## 3. お題の構造

### 3.1 3層に分ける

```
お題 = 骨格（型のテンプレート） × 素材（スロットに入る語） × 語尾（絞り込み）
```

これは調査で見つかった「要素 + お題語尾」の分解を、そのまま機械可読にしたもの。
**3層を独立に回すことが、A の新鮮味の土台**になる。同じ骨格でも素材が違えば別のお題に見え、
同じ素材でも語尾が違えば別の問いになる（「コンビニ、どんなの？」と「コンビニ、名前は？」は別物）。

### 3.2 データ形式

```jsonc
// data/topics/patterns.json — 骨格。スロット名と cat の対応はファイル頭の slotCats に1回だけ書く
{
  "id": "at-02",
  "type": "attr",                              // §2.1 の型
  "template": "{TIME}にしか営業していない{ORG}。{E}",
  "slots": ["TIME", "ORG"],
  "endings": [                                 // 文字列でも、条件付きのオブジェクトでもよい
    { "text": "どんな{ORG}？" },
    { "text": "何を売っている？", "require": { "ORG": ["sells"] } }
  ],
  "deny": { "THING": ["fixed"] },              // 文法が壊れる素材を締め出す（§5.2）
  "maxLen": 32,
  "why": "なぜこの骨格を置いたか。消すか残すかを後で判断するために書く"
}
```

```jsonc
// data/topics/words/*.json — 素材
{
  "id": "w-0143",
  "word": "部長",
  "cat": "person",                // person / place / org / thing / act / attr / time / rule
  "tags": ["職場", "大人"],
  "roles": [],                    // 文法上の性質（§5.2）
  "level": 1,                     // 1=誰でも知っている  2=少し狭い  3=固有名詞・時事
  "avoid": false                  // §7 の除外フラグ
}
```

```jsonc
// data/topics/endings.json — 語尾
{ "id": "e-attr-1", "text": "どんな{B}？", "tightness": 2 }  // 1=委ねる 〜 3=強く絞る
```

- `level` は「誰でも知っとる題材を選ぶ」という現場の原則の実装。
  **既定は level 1 を中心にし、2 を25%、3（固有名詞・時事）を4%まで**。
  4%は実測の固有名詞使用率4.4%に合わせた。**毎回だと安っぽく、たまに来ると効く**比率。
- `level: 3` は陳腐化する。**ファイルを分けて、そこだけ差し替えられるようにする。**

## 4. 生成アルゴリズム

```
nextTopic(rng, history, brought):
  0. 30%の確率で「持ち寄り語を使う回」に決める（§5.1）
  1. 型を選ぶ
       §2.1 の重み × 直近の使用による減衰（1問前 ×0.10 / 2問前 ×0.35 / 3問前 ×0.65）
       引き直しで捨てた型は、さらに6問ぶん減衰を伸ばす（§4.2）
  2. 骨格を選ぶ
       その型の patterns から、直近6問で使った pattern.id を除外
       残ったうち、いちばん長く出ていない骨格を採る（同率なら乱択）
       引き直しで捨てた pattern.id はこの部屋では二度と使わない
  3. スロットを埋める
       未使用プールから §5 の組み合わせ規則を満たす語を引く
       「持ち寄り語を使う回」なら、1スロットだけ持ち寄り語に差し替える
  4. 語尾を選ぶ
       その骨格の endings から、直近5問で使った語尾を除外
  5. 修飾レイヤを適用（§6）
  6. 文字数が pattern.maxLen を超えたら破棄
  7. 1〜6 を最大 M=8 回まわし、直近 K=6 問との「近さ」が最小の候補を採る
```

### 4.0 型は「除外」せず「減衰」させる

最初は「直近3問に出た型を除外」で書いていた。**下見の50問でこれが破綻した。**

除外方式だと、重い型ほど頻繁に使われ、頻繁に使われるほど頻繁に除外される。
そこへ §4.1 の「近さ」が型の一致をさらに罰しにいくので、
**重み表と型クールダウンと近さ計算の3つが同じ仕事を三重にやる**ことになる。
結果、狙い 18% の設定提示型が 12%、狙い 4% のあるある型が 8% と、分布が均等に潰れた。
重み表が事実上無視されていた。

減衰方式に変えると、40問で狙い 18/18/13/12/10/8/8/6/4 に対して
実際 15/15/13/13/10/10/10/8/8 まで寄った。**近さ計算の型一致も 5 → 3 に下げてある。**

同じ「散らす」仕事を複数の仕掛けにやらせない。

### 4.1 「近さ」の測り方

新鮮味を守るには、生成のランダム性を上げるのではなく**反復を検出して避ける**方がよい。
ランダム性を上げると、意味の壊れたお題（＝答えられないお題）が増えるだけで、
それは新鮮味ではなく事故になる。

直近K問それぞれとの近さを足し合わせ、合計が最小の候補を選ぶ。

| 一致したもの | 加点 |
|---|---:|
| 型が同じ（§4.0 で 5 から下げた） | 3 |
| 骨格（pattern.id）が同じ | 4 |
| 語尾が同じ | 3 |
| 素材語が1つ同じ | 2 |
| 素材のタグが1つ同じ | 1 |

M=8 の候補を作って最小を採るだけで、直近との衝突はほぼ消える。
**M も K も定数として1箇所に置き、監査（§8）で調整する。**

### 4.2 引き直されたお題は、重く避ける

引き直し（[SPEC.md](./SPEC.md) §7）で捨てられたお題は、**全員が「これは違う」と言ったお題**。
ただ履歴に入れるだけでは足りない。

- 捨てたお題の**型は、減衰（§4.0）を6問ぶんに伸ばす**。
- 捨てたお題の**骨格（pattern.id）は、その部屋では二度と使わない。**
- 捨てたお題の**素材は使用済みのまま**にする（§4.3）。引き直したのに同じ語が
  戻ってきたら、引き直した意味がない。
- §4.1 の「近さ」の計算では、捨てたお題との一致を**2倍で数える**。

引き直しが続く（例えば3回連続）ようなら、それは生成が場と噛み合っていない合図。
**次のお題は手書き（§9）から出す。** 骨格をいじって粘るより、確実な札を切る。

### 4.3 素材は非復元で引く

**一度お題に使った語は、その部屋が生きているあいだ再利用しない。**
「またこの単語か」は、型の反復よりも強く飽きを呼ぶ。

プールが尽きたら、最も古く使った語から順に復活させる（枯れたことは画面に出さない）。
1部屋のお題数はせいぜい10〜30問なので、素材が各カテゴリ200語もあれば実質尽きない。

## 5. 素材の組み合わせ規則

要素は**2つを基本、多くて3つ**（3つが限界という現場の共通見解に従う）。
ランダムに2語引くと、近すぎて平凡（同カテゴリ・同タグ）か、遠すぎて意味不明になる。

**規則: `cat` が異なり、`tags` が1つ以上重なる組を選ぶ。**

- 種類は違うが同じ場を共有している ＝ **意外だが答えられる**。ここが新鮮味の主エンジン。
- 例: `部長`(person / 職場) × `始業のチャイム`(thing / 職場) → 場が同じ、種類が違う。
- 例（避ける）: `部長`(person / 職場) × `課長`(person / 職場) → 近すぎて平凡。
- 例（避ける）: `部長`(person / 職場) × `マントル`(thing / 地学) → 共通タグ0で足場がない。

ただし **8%だけ、共通タグ0の遠い組を許す**。全部を「答えられる」に寄せると予定調和になる。
事故も新鮮味のうちだが、少量に留める。

### 5.1 持ち寄り語

ロビーで各自が入れた語（[SPEC.md](./SPEC.md) §9.2）を素材プールに混ぜる。
**自動生成だけでは絶対に届かない当たりが、ここから出る。**

#### tags の条件は免除する

持ち寄り語には `tags` が無い。プレイヤーに単語ごとのタグまで付けさせるのは無理がある。
したがって §5 の「共通タグが1つ以上」を満たせない。

**免除してよい。** あの規則が要るのは、一般語どうしに共有文脈が無いと足場が消えるから
（`部長` × `マントル`）。持ち寄り語は**その部屋の全員が意味を知っていることが保証されている**ので、
どれだけ遠くても足場がある。むしろ遠いほど効く。

- 持ち寄り語が入るスロットには `cat` の条件だけを課す。
- もう片方のスロットは通常素材から、`cat` が違うものを引く。

#### 種類はプレイヤーに選ばせる

入力時に **だれ / どこ / なに / すること** を1タップで選ばせ、`cat` にする
（`person` / `place` / `thing` / `act`）。

推測で埋めない。品詞や意味を機械で当てにいくと
「部長が始業のチャイムを退職した」のような文が出て、お題が死ぬ。
1タップの手間の方が安い。

#### 出しすぎない

| 項目 | 値 | なぜ |
|---|---:|---|
| 持ち寄り語を含むお題の割合 | 30% | 毎回だと8語程度のプールが即枯れる。3問に1問で十分効く |
| 1つのお題に入る持ち寄り語 | 最大1 | 2つ入ると内輪ネタ同士がぶつかって、お題ではなく暗号になる |
| 引き方 | 非復元（§4.3 と同じ） | 同じ語が続けて出ると、持ち寄りの驚きが一度で終わる |

`level` は 1 として扱う（全員が知っている前提なので）。

#### 監査で見る

`topics:audit`（§8）に、持ち寄り語ありの比率と、語ごとの登場回数の偏りを足す。
8語中1語だけが5回出る、のような偏りは非復元でも起きる（型との相性で引かれ方が偏る）。

---

### 5.2 役割（roles）— cat と tags では足りなかった

**下見で最初に出た壊れ方は、意味ではなく文法だった。**

> 停電中にしか営業していない引っ越し業者。**何を売っている？**
> 陽気な給食のおばさんに**断食されたくない**。なぜ嫌？
> 執事が**押し入れに来なくなった**。なぜ？
> 部長が会議室に**持ち込んだ非常ベル**。

`cat` は合っている（org / act / place / thing）。`tags` の足場もある。それでも壊れる。
骨格の動詞と語尾が、素材に**文法上の性質**を要求しているのに、それを持っていないからである。

そこで語に `roles` を足し、骨格側から締め出せるようにした。

| role | cat | 意味 | 効く骨格 |
|---|---|---|---|
| `sells` | org | 商品を売る | at-02 の語尾「何を売っている？」が `require` |
| `noplace` | org | 物理の拠点を持たない（町内会・部活・引っ越し業者） | st-04「{ORG}に置いてある」/ at-01「経営している」/ li-05 |
| `personal` | act | 組織が主語になれない（潜入・家出・再婚） | wh-02「{ORG}が急に{ACT}を始めた」 |
| `intrans` | act | 受身にできない（断食・挙手・号泣） | （ha-02 とともに廃止。素材側の印は残す） |
| `nook` | place | 人が通う場所ではない（押し入れ・廃校・洞窟） | wh-01「{PLACE}に来なくなった」/ bl-02 |
| `private` | place | 自分の生活空間（実家・台所・給湯室） | at-04「{PLACE}で拾った」/ bl-02「看板」 |
| `pub` | place | 自動販売機が置かれうる公共の場 | nm-02 が `require` |
| `fixed` | thing | 持ち歩けない（非常ベル・消火器・加湿器） | ac-02「落とした」/ at-05「持ち込んだ」 |
| `guest` | person | その場面にしか居ない人（面接官） | wh-01 |
| `moment` | time | 場面依存の相対時（面接の最中・閉店の10分前） | ha-03「こんな{TIME}の{PLACE}」/ st-05 |

**この表は下見のたびに伸びる。** 1回目で4つ、2回目で6つ増えた。
`cat` と `tags` だけで文が通ると思ってはいけない、というのがここまでで一番大きな学びになった。

- **`deny` を主に使う。** 「通う場所」を積極的に付けると28語中25語に付くことになる。
  例外の方が少ないので、例外だけを印す。
- **`require` は語尾にも書ける。** at-02 は「どんな〜？」なら誰でもよく、
  「何を売っている？」のときだけ `sells` が要る。**制約は骨格ではなく語尾に紐づく**ことがある。
- **これは §5 の組み合わせ規則とは別のレイヤ。** §5 は「意外だが答えられるか」という
  面白さの話、`roles` は「日本語として言えるか」という文法の話。混ぜない。
- **持ち寄り語には `roles` を付けられない**（プレイヤーに聞けるのは種類の1タップまで）。
  したがって **`deny` や `require` が掛かっているスロットには持ち寄り語を入れない。**

## 6. 修飾レイヤ

骨格・素材・語尾とは独立に、確率で乗せる装置。**実測の比率をそのまま採用する。**

| 装置 | 確率 | 例 | 根拠 |
|---|---:|---|---|
| 「」で状況やセリフを埋め込む | 20% | 〜と言われた。 | 実測20.0%。どの型にも乗る |
| 仮想改変（もしも／未来の／新型の） | 4% | 新型の〜 | 実測3.9% |
| 固有名詞を混ぜる（level 3） | 4% | — | 実測4.4% |

いずれも**低い比率であることに意味がある**。毎回付けると骨格が透けて安っぽくなり、
まったく無いと単調になる。実測がこの比率に落ち着いているのは、そういうことだと解釈した。

## 7. 自動生成の事故を止める

ランダム合成は、身内で遊ぶ場に出したくない組み合わせを必ず作る。
面白さの問題ではなく、場が止まる問題なので、機械的に止める。

- 素材語に `avoid: true` を立てられるようにし、立った語は生成に使わない。
- `data/topics/blocklist.json` に**禁止ペア**（この語とこの語は組ませない）と
  **禁止語**（生成後の完成文に含まれていたら破棄）を持つ。
- 破棄したら §4 の M 回のループに戻る。M 回とも駄目なら手書きお題（§9）に落とす。
- **持ち寄り語も同じ blocklist を通す。** ロビーで受け取った時点で1回、
  お題に組んだ完成文でもう1回見る。身内で遊ぶ場なので入力そのものは信用してよいが、
  「入れた語」と「組み合わさった結果」は別物なので、両方見る。

これは面白さの検閲ではなく、**場が止まるのを防ぐための機械的な足切り**。
面白いかどうかの判断は人がやる（引き直しがそのための道具・[SPEC.md](./SPEC.md) §7）。

## 8. 枯れの監査

**生成の質は、目で50問見るまで分からない。** その代わり、反復だけは機械で測れる。

`npm.cmd run topics:audit` で1000問を生成し、以下を出す。

- 型の分布と、§2.1 の狙いとのずれ
- 語尾の上位10とその偏り（実測では語尾がごく少数の定型に集中していた。同じ形にならないか）
- 素材語の再訪率、直近6問以内での 型／骨格／語尾／素材 の重複率
- 文字数の分布（狙い18〜32字）と上限超過で破棄された率
- 持ち寄り語ありのお題の比率（狙い30%）と、語ごとの登場回数の偏り（§5.1）
- **無作為50問の本文をそのまま出力**。ここは人が読む

数字が緑でも面白いとは限らないので、**50問の目視を必ず通す**。

## 9. 手書きお題を混ぜる

**完全自動生成には必ず天井がある。** 骨格の数が有限なので、遊び込めば見破られる。

`data/topics/handmade.json` に手書きの完成お題を置き、**生成物と 25% 前後の割合で混ぜる**。
プレイヤーからは区別が付かない。骨格が透けたときの逃げ道として、いちばん費用対効果が高い。

手書き分にも  によるクールダウンを効かせ、同じ部屋で二度出さない。

### 9.1 参加者が手書きお題を投稿できる（実装済み・2026-08-29）

**プレイヤー自身が手書きお題を投稿できるフォームを用意する。** 自動生成の天井を越える手段として、
持ち寄り語（入口）・引き直し（出口）に続く3つ目になる。

- 投稿されたお題は `handmade.json` と同じ扱いで、生成物に混ざって出る。
- 誰が投稿したかは出さない。自分のお題が場に出たときの気まずさと面白さを残す。
**決めたこと:**

| 項目 | 決定 | なぜ |
|---|---|---|
| 置き場 | **部屋ごと**（サーバー共通にしない） | 持ち寄り語とまったく同じ扱いで済む。部屋の状態はもともとメモリにしか無いので、貯める前提にすると保存と検閲の話が別に要る |
| いつ出せるか | **ロビーでもゲーム中でも** | お題を思いつくのは遊んでいる最中だから。ゲーム中は畳んだフォームにする |
| 本文の配り方 | **自分が出した分だけ本人に返す。他人の本文は配らない** | 出るまで知らないから面白い。件数だけ全員に見せる |
| 消せる人 | 本人だけ（持ち寄り語と違い、ホストも消せない） | 本文を見られない以上、ホストが選別する意味がない |
| 上限 | 1人5問 / 4〜60文字 / 同じ文は1つだけ | 面白いかどうかは人が判断する。外れたら全員で引き直せばいい |
| 混ざり方 | **25%**。直前が手書きなら続けない | 人の札ばかりだと自動生成の意味がなくなる |
| 引き直しが3回続いたら | **確実に手書きから出す**（§4.2） | 生成が場と噛み合っていない合図。骨格をいじって粘るより確実な札を切る |

サーバー共通の置き場（資産として貯める）は、遊んでみて足りないと感じたら考える。

> **収集した3,240題は、そのままお題データにしない。**
> 他人が作った創作物なので、同梱して配るのは筋が違う。
> あの調査から使ってよいのは**型・語尾・比率といった傾向**であって、お題の文そのものではない。
> `handmade.json` は自分で書く。

## 10. 画面から来る制約

お題は `open` と `stage` で2回、暗い画面に大きく出る（[SPEC.md](./SPEC.md) §3.2）。
読み上げる人はいないので、**一目で読み切れる長さ**に収める。

| | 狙い | 上限 |
|---|---|---|
| 疑問符で締める型 | 18〜28字 | 32字 |
| 設定提示型（体言止め） | 20〜36字 | 45字 |

実測はネット24.4字・生29.7字。生側は40字超が18.4%あるが、あれは読み上げのある場の数字なので採らない。
上限超過は §4 の手順6で破棄する。切り詰めない（切ると意味が壊れる）。

## 11. §9 の境界との対応

[SPEC.md](./SPEC.md) §9 で切った境界は変えない。

```ts
// src/engine/topic.ts
export type Topic = { id: string; text: string };

export function nextTopic(
  rng: Rng,
  history: readonly TopicRecord[],
  brought: readonly BroughtWord[],
): TopicRecord;
```

§4 のクールダウンは「型・骨格・語尾・素材」を見るので、`history` に生成の内訳が要る。
`Topic` を外向きの型のままにして、**内訳は `TopicRecord` に持つ**。

```ts
// viewFor では Topic の分（id と text）まで削ってから配る
type TopicRecord = Topic & {
  patternId: string;
  type: TopicType;
  endingId: string;
  wordIds: string[];
  broughtIds: string[];   // 使った持ち寄り語（§5.1）
  discarded: boolean;     // 引き直しで捨てられたか（§4.2）
};

// 持ち寄り語。cat はプレイヤーが1タップで選んだもの
type BroughtWord = {
  id: string;
  word: string;
  cat: 'person' | 'place' | 'thing' | 'act';
};
```

`brought` は部屋が持つ（ロビーで集める）。**`nextTopic` は受け取るだけで、
プール自体は書き換えない。** 使用済みの印は `history` から導出する
（`broughtIds` を見れば分かる）。純粋関数のままにしておくため。

`nextTopic` は純粋関数のまま（`rng` を受け取り、外の状態を読まない）。
**乱数シードはサーバーだけが持ち、クライアントに配らない**（[SPEC.md](./SPEC.md) §8.4）。

## 12. 作る順番

1. ✅ `patterns.json` を **31骨格**、素材を**各カテゴリ25〜32語**で動かした（2026-08-29）。
   `node scripts/preview-topics.mjs --n 50 --seed 1 [--brought]` で読める。
   **骨格の本数は型の重みに比例させる。** 重み18の設定提示型に4本しか無いと、
   50問中9回出るうちの同じ骨が3回透ける。1骨格あたり2回までに収まる本数を持つ。
2. `topics:audit` を作り、反復の数字を見ながら M / K / 重みを詰める。
3. `handmade.json` を30題書いて混ぜる。
4. **持ち寄り語**を通す（§5.1）。骨格側に「どの `cat` でも受けられるスロット」が
   何本あるかで効き方が変わるので、骨格ができてからやる。
5. 遊んで、飽きるまでの問数を測る。骨格を増やすか手書き比率を上げるかは、その結果で決める。
   **引き直しの回数がいちばん正直な指標になる**（[SPEC.md](./SPEC.md) §7）。
   どの型・どの骨格で引き直されたかをログに残しておくと、次の手が決めやすい。

**先に素材を1000語書かない。** 骨格が悪いと、素材をいくら増やしても同じ顔のお題が出続ける。

## 13. 採用済み・保留

### 採用（2026-08-29）

| 提案 | どこに入ったか |
|---|---|
| **お題の引き直し** | [SPEC.md](./SPEC.md) §7 ／ 生成側の避け方は §4.2 |
| **プレイヤーが素材語を投入する（持ち寄り語）** | [SPEC.md](./SPEC.md) §9.2 ／ 生成側の扱いは §5.1 |

この2つは**同じ穴を別々に塞いでいる**。自動生成の天井を、
持ち寄り語は**入口**（素材そのものを人が入れる）から、
引き直しは**出口**（出てきた外れを人が捨てる）から越える。片方だけでは片手落ちになる。

### 保留（ルールに触るので、遊んでから決める）

| 提案 | 何が良いか | 何が要るか |
|---|---|---|
| **難度のノブをロビー設定にする** — 「やさしめ／おまかせ／委ねる」で語尾の絞り込み度と要素数を切り替える | 初対面の回と、慣れた面子の回で最適が違う（競技／娯楽の軸そのもの） | ロビーに設定が増える。既定は「おまかせ」 |
| **同じお題で回答が3回を超えたら補助線を1行足す** | B の枯れに直接効く | お題が途中で変わることになる。好みが分かれる |

引き直しの実測（§12 の手順5）を見てから決める方が早い。
外れの頻度が分かる前にノブを増やすと、何を回せばいいのか分からないノブになる。
