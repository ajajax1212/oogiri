# 大喜利（仮題） — 仕様書 v0.1

作成 2026-08-29

---

## 1. 概要

自動生成されたお題に対し、各プレイヤーが自分の端末で**フリップ**（手書き＋文字）を書き、
好きなタイミングで名乗り出て回答し、他のプレイヤーが**小笑い・中笑い・大笑い**の3段階で
採点するパーティーゲーム。PCブラウザ・各自の端末で遊ぶオンライン専用。

点数を機械的に計算するゲームではない。アプリはお題の供給・フリップの配布・採点の集計だけを
担当する。面白いかどうかを決めるのは人間で、アプリはその判定を邪魔しないことを目標にする。

### この設計の背骨

- **回答は競争ではなく持ち回りでもない。** 書けた人から名乗り出る。回答権に上限はなく、
  1つのお題で同じ人が何度回答してもよい。「回すゲーム」ではなく「場に出すゲーム」。
- **お題を切り上げるのは全員の合意。** 誰か1人が飽きても進まないし、
  全員が「もういい」と言うまでは何度でも回答できる。
- **積み上げるのは点ではなく「満点大笑い」の回数。** 通算点も順位表も出さない。
  順位を出すと、面白さの判断が数字の最適化に寄る。

### 想定プレイ人数

- **2〜10人**。推奨は **3〜6人**。
- 回答者1人 + 採点者1人以上で成立する。採点者が0人になった回答は「判定なし」として扱う（§6.5）。

## 2. 用語

| 用語 | 意味 |
|---|---|
| お題 | 自動生成された1問。全プレイヤーに共通 |
| お題セッション | 1つのお題が出てから、全員が「次のお題に行く」を押すまでの区間。中に回答が何回でも入る |
| フリップ | 各プレイヤーが書く1枚の板。手書きの線と文字要素を同じ面に混在できる（§4） |
| 回答 | フリップ1枚を場に出す一連の流れ。宣言 → 公開 → 採点 → 判定 の4段階（§5・§6） |
| 回答者 | その回答でフリップを出している人。1つの回答につき常に1人 |
| 採点者 | その回答の回答者以外で、接続しているプレイヤー全員 |
| 判定 | 採点の平均から決まる4種の結果。小笑い / 中笑い / 大笑い / 満点大笑い |
| 満点大笑い | 採点者全員が「大笑い」を選んだ状態。回数だけがプレイヤーに積み上がる |
| 持ち寄り語 | ロビーで各自が入れる単語。お題の素材に混ざる（§9.2） |
| 投稿お題 | 参加者が自分で書いて出したお題。自動生成に混ざって出る（[TOPIC-GEN.md](./TOPIC-GEN.md) §9.1） |
| 引き直し | まだ回答が出ていないお題を、全員の合意で捨てて別のお題に差し替えること（§7） |

## 3. 画面の流れ

### 3.1 部屋の状態（`room.phase`）

```
lobby ──host:start──> live ──host:toLobby──> lobby
```

- `lobby` — 名前を入れて集まる。ホストだけが開始できる。
- `live` — お題セッションが連続する。終了条件は無い。ホストが `toLobby` で切り上げる。

### 3.2 お題セッションの状態（`topic.phase`）

1つのお題の中で、回答が入るたびに `open` から一周して `open` に戻る。

```
  intro ──5.2秒──> open ──ANSWER_CLAIM──> declared ──2.0秒──> stage
（全画面のお題）      │  ▲                                        │
                     │  │                                  ANSWER_REVEAL
                     │  │                                        ▼
                     │  └── 4.5秒 ── result <── 1.2秒 ── tally <── reveal
                     │                                （採点者が全員押した）
                     │
                     └─ 全員が NEXT_READY かつ open ──> 次のお題へ（新しい intro）
```

| phase | 全員の画面 | 誰が何をできるか |
|---|---|---|
| `intro` | **新しいお題が全画面で大きく出る** | 何もできない。5.2秒で自動的にボードへ移る |
| `open` | お題は上に小さく。自分のフリップを書ける | 誰でも「回答する」を押せる。先着1人だけ通る |
| `declared` | 「〇〇さんが回答します」だけ | 何もできない。2.0秒で自動的に次へ |
| `stage` | お題が再表示される | 回答者だけが「公開する」を押せる |
| `reveal` | 回答者のフリップが全画面に出る | 採点者が小笑い／中笑い／大笑いを1回押す |
| `tally` | 「集計中」 | 何もできない。1.2秒で自動的に次へ |
| `result` | 判定が出る。満点なら「満点大笑い」の演出 | 4.5秒で `open` に戻る |

- **`declared` `tally` `result` の待ち時間はサーバーが持つ**（§8.3）。演出のための間なので、
  数字は後から調整してよい。クライアント側のタイマーで進めてはいけない。
- **`open` 以外の間も、回答者以外は自分のフリップを書き続けられる。**
  他人が回答している最中に次のネタを仕込めるのが、このゲームの待ち時間の使い方になる。
- **画面最下部の合意ボタン（「お題を引き直す」／「次のお題に行く」）はどの phase でも押せる**（§7）。

## 4. フリップ

### 4.1 中身の持ち方

フリップは画像ではなく**構造データ**として持つ。

```ts
type Flip = {
  strokes: Stroke[];   // 手書きの線
  texts: TextItem[];   // 文字要素
};

type Stroke = {
  color: 'black' | 'red' | 'blue';
  width: 1 | 2 | 3;             // 細 / 中 / 太
  points: number[];             // [x0,y0,x1,y1,...] 論理座標
};

type TextItem = {
  text: string;                 // 最大60文字
  x: number; y: number;         // 中心座標
  size: 1 | 2 | 3;              // 小 / 中 / 大
};
```

- **PNG の dataURL で持たない。** 1枚あたり数百KBになるうえ、拡大するとぼけ、
  後から文字だけ動かすこともできない。線と文字のままなら通信は数KBで済み、
  どの画面サイズでも綺麗に出る。
- **論理座標は 1600 × 1000 固定**（16:10）。表示側は CSS で縮めるだけにする。
  座標を画面サイズに依存させると、書いた人と見る人で位置がずれる。

### 4.2 書き方

- **手書き** — マウスのドラッグで線を引く。色3種・太さ3段。
  「1つ戻す」（ストローク単位の undo）と「全部消す」。消しゴムは持たない
  （マウスで細かく消すのは実際やりにくいので、戻すで足りる）。
- **文字** — 入力欄に打って「フリップに乗せる」で文字要素になる。
  乗せた後はドラッグで移動、サイズ3段、選択して削除できる。
- **手書きと文字は1枚に混在できる。** 絵に一言添える、書いた文字に丸を付ける、
  といった回答を通すため。描画順は「手書き → 文字」で、文字が常に上に出る。

### 4.3 入力の下限

「回答する」ボタンは**フリップが空でない**ときだけ押せる。
空でない = ストロークが1本以上、または文字要素が1つ以上。

これはクライアントでボタンを無効化するだけでなく、**サーバー側でも同じ条件で弾く**。
通信を直接叩けばボタンの無効化は素通りする。

### 4.4 サーバー側の上限（検証）

`ANSWER_CLAIM` で受け取ったフリップは、以下を全て満たさなければ拒否する。

| 項目 | 上限 |
|---|---|
| ストローク数 | 2000 |
| 全ストロークの点数の合計 | 40000（= 座標値 80000 個） |
| 文字要素の数 | 10 |
| 1文字要素の文字数 | 60 |
| 座標値 | 有限の数値かつ盤面の範囲内。外れていたら拒否（丸めない） |

上限に引っかかったら回答権を渡さず、その人にだけエラーを返す。
座標を勝手に丸めて通すと、書いた本人の画面と場に出る絵が食い違う。

### 4.5 書きかけのフリップはサーバーに置かない

各プレイヤーの書きかけは**クライアントの `sessionStorage`** に持つ。サーバーへ送るのは
`ANSWER_CLAIM` の一度だけ。

- 書いている途中の中身は、どのタイミングでも他人に配られない。サーバーに存在しないので、
  通信を覗いても漏れない。
- リロードしても書きかけは残る（`sessionStorage` なので、同じブラウザの2つ目のタブが
  先の内容を奪うこともない）。
- ただし、**他人が「今書いているかどうか」の真偽値だけは配る**。「3人が書いています」と
  出すだけで場が温まる。中身は一切含めない。

### 4.6 いつ消えるか

| きっかけ | 自分のフリップ |
|---|---|
| 「回答する」が通った | 確定して**編集不可**になる。判定が終わったら空になる |
| 「回答する」を他人に取られた | そのまま残る。書き続けられる |
| 次のお題に進んだ | 空になる |

**`ANSWER_CLAIM` を押した後は書き直せない。** `stage`（お題の再表示）で書き直せると、
全員が待っている前で無限に粘れてしまう。名乗り出るのは書き終わってから。

## 5. 回答する

### 5.1 回答権は先着1人

`open` の間、誰でも「回答する」を押せる。**サーバーが最初に受け取った1人だけ**が回答者になり、
`topic.phase` は `declared` へ移る。以降の `ANSWER_CLAIM` は
「今は他の人が回答しています」で弾かれる。

- 順番待ちの列は作らない。先に押した人が終わったら、また全員のボタンが復活する。
  列にすると「押したのに取り消せない」問題と「並んでいる間に思いつきが古くなる」問題が出る。
- 回答権は無限。同じ人が続けて何度取ってもよい。回数の制限を入れない。

### 5.2 「〇〇さんが回答します」

`declared` の 2.0 秒間、全員の画面が回答者の名前だけになる。お題もフリップも出さない。
ここで場の視線を集めてから、`stage` でお題を出し直す。

### 5.3 「公開する」

`stage` では**回答者だけ**に「公開する」ボタンが出る。押すと `reveal` へ移り、
全員の画面に同じフリップが出る。

回答者が `declared` / `stage` の間に切断した場合、**5秒の猶予の後に回答権を解放**して
`open` に戻す。確定済みのフリップは破棄する。
`reveal` まで進んでいれば、すでに全員が見ているので採点は続行する。

## 6. 採点と判定

### 6.1 採点者

その回答の**回答者以外で、接続しているプレイヤー全員**。回答者は自分の回答を採点できない。

### 6.2 採点ボタン

`reveal` の間、フリップの下に3つのボタンを出す。

| ボタン | 値 |
|---|---|
| 小笑い | 1 |
| 中笑い | 2 |
| 大笑い | 3 |

**1人1回。押したら変更も取り消しもできない。** 押し直せる仕様にすると、
他人の押した数を見ながら空気を読んで動かす余地が出る。押した瞬間に確定させる。

採点中に全員へ配るのは「**何人が押したか**」だけ。誰が何を押したかは、確定後も配らない。

### 6.3 いつ確定するか

**回答者以外の接続中プレイヤー全員が押した瞬間**に自動で確定し、`tally` へ移る。

- 採点中に誰かが切断したら、その人は必要人数から外れる。残り全員が押していればそこで確定する。
- 押した後に切断した人の票は**有効なまま残す**。押した事実は取り消さない。
- 制限時間は置かない。急かすと、考えて押す余地が消える。

### 6.4 集計

```
合計 = 押された値の合計
n    = 実際に押した採点者の数
平均 = 合計 / n
```

判定は平均を [1, 3] の3等分で切る。境界は浮動小数点で比べず、**整数のまま判定する**
（`合計 * 3 >= 7 * n` のような形）。0.1 の誤差で判定が変わるのを避けるため。

| 条件 | 判定 |
|---|---|
| `合計 === 3n`（全員が大笑い） | **満点大笑い** |
| `合計 * 3 >= 7n`（平均 ≧ 2.334） | 大笑い |
| `合計 * 3 >= 5n`（平均 ≧ 1.667） | 中笑い |
| それ以外 | 小笑い |

`result` では判定に加えて**内訳の分布**（小◯・中◯・大◯）を出す。誰が押したかは出さない。

### 6.5 採点者が0人のとき

全員が切断して回答者しか残っていない場合、判定は行わず `result` に「判定なし」と出す。
満点大笑いのカウントも動かない。

### 6.6 満点大笑いの回数

判定が「満点大笑い」だったとき、**回答者の満点回数を +1** する。

- プレイヤー名の横に回数を出す（0 のときは何も出さない）。
- ホストが `toLobby` で部屋をロビーに戻したときにリセットする（持ち寄り語は残す・§9.2）。
- **これ以外の得点・順位・通算表は一切持たない。**

## 7. 次のお題に行く / お題を引き直す

### 7.1 ボタンは1つ。ラベルが変わる

画面最下部のボタンは**常に1つだけ**。そのお題で**回答が1件でも公開されたか**でラベルが変わる。

| そのお題の回答 | ラベル | 意味 |
|---|---|---|
| 0件 | **お題を引き直す** | このお題は外れ。捨てて別のを出す |
| 1件以上 | **次のお題に行く** | このお題は遊んだ。次へ |

**2つのボタンを並べない。** 並べると、回答0件の場面で「引き直す」派と「次へ」派に票が割れ、
どちらも全員に届かないまま膠着する。動作はどちらも「新しいお題を出す」で同じで、
分ける必要があるのは**捨てたお題を以後どう避けるか**だけ
（[TOPIC-GEN.md](./TOPIC-GEN.md) §4.2）。

引き直しの回数に上限は置かない。全員の合意が要る以上、荒らせない。

### 7.2 押し方

- **どの phase でも押せる。**
- 押すと自分に印が付く。**もう一度押すと取り消せる**（気が変わることはある）。
- 誰が押したかは全員に見える（「3 / 5人」と、名前の脇の印）。
- **全員が押していて、かつ `topic.phase === 'open'` のとき**に新しいお題へ進む。
  - 回答が進行中（`declared`〜`result`）のときは、最後の1人が押しても進まない。
    その回答の判定が出て `open` に戻った瞬間に進む。出ている回答を途中で消さないため。
- **全員に揃うまでは回答できる。** 押した人も「回答する」を押せる。
  押した場合、その人の印は自動的に外れる（回答したいのに次へ行くのは矛盾しているので）。
- 途中から入ってきた人は押していない状態で入る。
- 切断中の人は人数から外す（1人落ちただけで永久に進めなくなるのを避けるため）。

### 7.3 印を取り直すとき

| きっかけ | なぜ |
|---|---|
| 新しいお題に移った | 当然。あわせて全員のフリップを空にする |
| **そのお題で最初の回答が公開された** | ボタンの意味が変わるため（§7.1） |

「外れだから捨てよう」と「遊んだから次へ」は別の意思表示なので、
ボタンのラベルが変わる瞬間に印を取り直す。引き直しに同意していた人が、
知らないうちに「次へ」に同意したことにならないようにする。

## 8. サーバーとの通信

### 8.1 型は `ranking-tote` / `senryu-game` に合わせる

- **Express + Socket.IO。ページは1枚だけ。** `/` も `/g/<code>` も同じ SPA を返し、
  クライアントが URL から部屋コードを読む。**部屋の URL がそのまま招待状**になる。
- **状態はサーバーが持つ。** phase も時計もサーバー側。
- **再接続は `sessionStorage`。** 席の合鍵（token）で本人確認する。
  ID だけで席を渡すと `p0` `p1` は推測できる。
- **イベント名は `src/net/events.ts` の `EV` に集約**し、サーバーとクライアントの両方がそこから読む。

### 8.2 イベント

```ts
export const EV = {
  create:  'room:create',   // 部屋を作る → { ok, code, playerId, token }
  join:    'room:join',     // 部屋に入る → { ok, code, playerId, token }
  rejoin:  'room:rejoin',   // リロード後に元の席へ戻る
  leave:   'room:leave',    // 抜ける（ロビーにいる間だけ）
  word:    'room:word',     // 持ち寄り語を足す／消す（ロビーにいる間だけ・§9.2）
  start:   'host:start',    // ホストが開始
  kick:    'host:kick',     // ホストが切れた人を席から外す（ロビーにいる間だけ）
  toLobby: 'host:toLobby',  // ホストがロビーへ戻す（満点回数はリセット・持ち寄り語は残す）
  action:  'game:action',   // ゲーム中の行動
  state:   'state',         // サーバー → クライアント。1人分に絞った状態
} as const;
```

`game:action` で送る行動は4つだけ。

| action | 送る人 | 中身 | 通る条件 |
|---|---|---|---|
| `ANSWER_CLAIM` | 誰でも | `{ flip }` | `open` かつ 空でない かつ §4.4 を満たす。先着1人 |
| `ANSWER_REVEAL` | 回答者 | なし | `stage` |
| `SCORE` | 採点者 | `{ value: 1..3 }` | `reveal` かつ 未採点 かつ 回答者でない |
| `NEXT_READY` | 誰でも | `{ ready: boolean }` | `live` の間はいつでも。引き直しも次へも同じ action（§7.1） |

**上の「通る条件」は全てサーバー側で判定する。** クライアントのボタン制御はあくまで見た目で、
通信を直接叩かれたときの防御にはならない。

### 8.3 サーバーが持つ時計

| 遷移 | 既定値 | なぜサーバーが持つか |
|---|---|---|
| 新しいお題 → `open` | 5.2 秒 | 読み切る前にボードへ移ると、お題が頭に入らないため |
| `declared` → `stage` | 2.0 秒 | 回答者のブラウザが落ちた瞬間に全員の進行が止まるため |
| `tally` → `result` | 1.2 秒 | 同上 |
| `result` → `open` | 4.5 秒 | 同上 |
| 回答者の切断 → 回答権の解放 | 5.0 秒 | 一瞬の回線の揺れで回答権を落とさないため |

クライアントは `deadline`（絶対時刻）を受け取って残りを描くだけにする。

### 8.4 1人分に絞った状態（`viewFor`）

全員に同じ状態を配らない。`viewFor(state, me)` で以下を**落としてから**配る。

| 落とすもの | なぜ |
|---|---|
| 他人の書きかけのフリップ | そもそもサーバーに置かない（§4.5）。「書いているか」の真偽値だけ配る |
| 確定済み・未公開のフリップ | `stage` の間は回答者本人にだけ配る。他人に配ると公開前に読める |
| 採点の個票（誰が何を押したか） | 確定後も配らない。人数と分布だけ |
| お題生成の乱数シードと未使用のお題 | シードがあれば次のお題を先に計算できてしまう |

## 9. お題の自動生成

**設計は [TOPIC-GEN.md](./TOPIC-GEN.md) に分けた。** ここで固定するのは境界だけ。

### 9.1 関数の境界

```ts
// src/engine/topic.ts
export type Topic = { id: string; text: string };

export function nextTopic(
  rng: Rng,
  history: readonly TopicRecord[],
  brought: readonly BroughtWord[],   // 持ち寄り語（§9.2）
): TopicRecord;
```

- 呼び出し側（reducer）は `nextTopic` しか知らない。中でテンプレートを埋めようが
  辞書から引こうが、外の作りは変わらないようにしておく。
- `history` を渡すのは、直近に出たお題と、**引き直しで捨てたお題**を避けるため。
- **乱数はシード付きで、シードはサーバーだけが持つ**（§8.4）。
- `history` には型・骨格・語尾・素材の内訳（`TopicRecord`）を持たせるが、
  **`viewFor` では `Topic` の分（id と text）まで削ってから配る**。
  内訳が漏れると次のお題を計算できてしまう。

### 9.2 持ち寄り語

**ロビーで各自が単語を入れ、それがお題の素材に混ざる。** 内輪の言葉が骨格に乗るので、
自動生成だけでは絶対に届かない当たりが出る。新鮮味の源としては最も強い。

- **1人1語を必須、任意でさらに2語まで**（1人あたり最大3語）。ゲーム開始の条件は
  「全員が1語以上入れていること」。
- **入れられるのはロビーにいる間だけ。** `live` の最中は足せない。
  ホストが `toLobby` で戻したら、そこでまた足せる。
- **語といっしょに種類を1タップで選ぶ**（だれ / どこ / なに / すること）。
  お題の骨格のどのスロットに入れられるかを決めるのに要る。
  ここを推測で埋めると「部長が始業のチャイムを退職した」のような文が出る。
- **入れた語はロビーで全員に見える。誰が入れたかは出さない。**
  変な語をその場で止められるようにしつつ、お題に出たときの「これ誰の？」を残す。
- 入れた本人は自分の語を消せる（ロビーにいる間）。ホストは誰の語でも消せる。

#### 検証（サーバー側）

| 項目 | 上限・条件 |
|---|---|
| 1語の文字数 | 1〜12文字 |
| 1人あたりの語数 | 3 |
| 種類 | だれ / どこ / なに / すること のいずれか |
| 重複 | 同じ部屋に同じ語は1つだけ（先勝ち） |
| 禁止語 | [TOPIC-GEN.md](./TOPIC-GEN.md) §7 の blocklist を通す |

#### いつ消えるか

- ホストが `toLobby` でロビーに戻しても、**持ち寄り語は残す**（満点回数はリセットする）。
  せっかく入れた言葉を毎回入れ直させない。続きから足せる。
- 部屋が消えたら消える。サーバーのメモリにしか無い。

## 10. 画面デザイン

### 10.1 方針

『IPPONグランプリ』**風**の雰囲気に寄せる。**番組のロゴ・マーク・固有の書体そのものは使わない。**
寄せるのは配色と間の取り方だけにする。

- **背景** — 暗い紺〜黒のグラデーション。中央にスポットの当たった明るみ。
- **差し色** — 金（判定・満点の演出）。それ以外は極力使わない。
- **お題** — 画面の上寄りに、太い明朝で大きく。読ませる時間を作るため、出現時に軽く間を置く。
- **フリップ** — 白い板に黒の太いマジック。板には僅かな影と縁を付け、
  「物理の板を掲げている」感じを出す。回転や紙質のテクスチャまではやらない。
- **プレイヤー** — 画面下部に横一列のパネル。名前・満点回数・ready の印・「書いています」の印。

### 10.2 見せ場

| 場面 | 演出 |
|---|---|
| `declared` | 画面が暗転し、回答者の名前だけが大きく出る |
| `reveal` | 伏せた板が起き上がる。**ため → 一撃 → 止め**の3拍で、尺は効果音の波形に合わせる |
| `tally` → `result` | **1つの画面。フリップは出したまま、周りを金の枠が12段で囲っていく。** 止まった段が判定（小3 / 中6 / 大9 / 満点12）。溜めの長さは判定ごとに変え、乱数は回答者とお題から作るので**全員の画面で同じ瞬間に止まる** |
| `result`（小・中・大） | 判定の文字がスタンプのように出る |
| `result`（満点大笑い） | 金の演出を全画面で。ここだけ明確に他と格を変える |

満点大笑いだけは**音も演出も別格**にする。この4段目があることが、
3段階の採点に意味を持たせている。

**判定の音は枠が閉じ切るまで鳴らさない。** 先に鳴ると声で判定が分かる。
画と音は `src/ui/closing.ts` の同じ計算から時刻を読む（別々に出すと必ずずれる）。

**採点は板が止まるまで押させない。** 途中で最後の1人が押せてしまうと、
読む間が消えるうえ、判定の音が公開の音に重なって濁る。隠すときは
`visibility` も落とす（`opacity` だけだと見えないボタンが押せてしまう）。

### 10.3 音

- **依存は増やさない。** Web Audio を直接叩く（`senryu-game/src/ui/sound.ts` と同じ作り）。
- **既定はオフ。** ページを開いただけで音源を取りに行かせない。オンにした人の操作を待つ。
- 前回オンにしていた人（`localStorage`）は、開いた時点で読み込んでおく。
- 鳴らすのは お題 / 宣言 / 公開 / 集計 / 判定 / 板へ戻る に絞る。**場面が変わったときだけ**鳴らす。
- **判定のあと板へ戻ったときにも鳴らす。** 次を書ける合図が無いと、
  結果の余韻のまま「もう書いていいのか」が分からない。

## 11. 技術と構成

### 11.1 スタック

TypeScript / React 19 / Vite 6 / Express 4 / Socket.IO 4 / Vitest 2。ESM。
`senryu-game` と同じ構成にする。**`any` で逃げない。**

### 11.2 ディレクトリ

```
oogiri-game/
  src/engine/    ゲームのルール。React も Socket.IO も知らない純粋な層
    types.ts     Flip / Player / GameState / Phase / Action / Topic
    reducer.ts   (state, action) => state。ルールの本体はここだけ
    judge.ts     採点の集計と判定（§6.4）。整数のまま比べる
    topic.ts     お題の生成（§9）。持ち寄り語もここで素材に混ぜる
    view.ts      viewFor(state, me) — 1人分に絞った状態
  src/net/
    events.ts    EV の唯一の定義 + 入力の検証（フリップの上限など）
    useRoom.ts   接続・再接続・状態受信
  src/ui/
    Flip.tsx        フリップの描画（見るだけ）
    FlipEditor.tsx  フリップを書く（手書き + 文字）
    sound.ts        効果音（既定オフ）
  server/
    index.ts     Socket.IO のハンドラ。reducer と viewFor を呼ぶだけ
    rooms.ts     部屋・席・token・タイマー。ルールは持たない
  data/topics/   お題のもと
  docs/SPEC.md   これ
```

**層の境界を守る。** `src/engine/` にネットワークと React を持ち込まない。
ルールの変更は `reducer.ts` だけで完結させる。`server/rooms.ts` はゲームのルールを知らない。

### 11.3 ポート

| ポート | 用途 |
|---|---|
| 3600 | oogiri-game（本番と同じ構成のサーバー） |
| 5175 | oogiri-game の Vite 開発サーバー（クライアントのみ） |

### 11.4 デプロイ

GitHub → Render の無料プラン。`render.yaml` を同梱する。
**ビルドコマンドは `npm ci --include=dev`。** Render は `NODE_ENV=production` を既定で入れるので、
これを明示しないと `vite` と `tsc` が入らないままビルドに入って落ちる。

部屋の状態はメモリなので、インスタンスが落ちれば進行中のゲームは消える（許容する）。

**リポジトリは本人が GitHub 上で作る。** こちらは `git remote add` から先だけを担当する。

### 11.5 テストの方針

`src/engine/` が純粋なので、テストはここに寄せて書く。

- `judge.ts` — 境界値（平均 1.666… / 1.667 / 2.333 / 2.334）、満点、採点者1人、採点者0人
- `reducer.ts` — 回答権の先着（同時 `ANSWER_CLAIM` で2人目が弾かれる）、
  回答者の自己採点の拒否、二重採点の拒否、
  ready が全員かつ `open` のときだけ進む、回答中は進まない、回答すると ready が外れる、
  **最初の回答が公開された瞬間に ready が全解除される**（§7.3）、
  **回答0件で全員が押したら引き直し扱いになる**（捨てたお題が履歴に残る）
- `events.ts` — フリップの上限（§4.4）を超える入力の拒否、空フリップの拒否、
  持ち寄り語の検証（§9.2）
- `view.ts` — 未公開のフリップ・採点の個票・シードが他人に漏れないこと

**テストが通っただけでは「遊べる」ことの証明にならない。** 変更したら
`npm.cmd run build && npm.cmd start` で実際に複数タブから触って確かめる。
`npm.cmd run dev`（Vite）はクライアントしか立てないので、部屋が作れない。
